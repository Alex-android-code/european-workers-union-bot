# Кандидатний радар — MVP для перевірки

Окремий модуль EWU. Ця гілка не змінює запущений EWU, Railway-конфігурацію,
токен, стару базу або сценарій запуску. Production-команда залишається
`python railway_start.py`; новий модуль запускають тільки явно.

## Реалізовано

- Короткий український Telegram-сценарій: місто, графік, початок, потрібні навички,
  необов’язкове побажання щодо оплати. Вибір кількох вакансій, окреме ознайомлення
  зі згодою, власний контакт через кнопку Telegram, перегляд і відкликання заявок.
- Джерела `?start=src_<tag>`; мітка прив’язується до створеної заявки. Повторний
  відгук на ту саму вакансію не перезаписує початкове джерело. `/reset` зберігає
  мітку поточного звернення. Візити рахуються один раз на джерело/день/користувача;
  це переходи зі стартом бота, а не покази реклами або вимір усіх кліків на URL.
- Правила підбору використовують тільки погоджені робочі критерії. Стать, вік,
  громадянство, здоров’я та документи не є критеріями. Невідомі ставки, навички,
  графіки й дати позначаються для уточнення, а не вгадуються.
- Публічні дані, приватні примітки, сирі дані джерела та комісії лежать окремо.
  Публічний серіалізатор не завантажує приватні поля. Немає AI-викликів,
  рекламної публікації, розсилок, автоматичних рішень про найм або файлів кандидатів.
- Закритий адаптивний кабінет: вхід, перевірка/редагування вакансій, активність,
  пошук і фільтри заявок, контакт, історія, примітки, нові заявки, джерела і витрати,
  вартість кандидата на співбесіді та найнятого кандидата. Кілька заявок однієї
  людини не збільшують кількість кандидатів у показнику ціни співбесіди/найму.
- Серверна база, транзакції, контроль паралельних змін, відмітка можливого дубля
  за телефоном між різними Telegram-акаунтами без автоматичного злиття особистостей.
- Пароль scrypt, сесії в базі, HttpOnly/Secure/SameSite cookie, CSRF та точна
  перевірка Origin, обмеження спроб входу, CSP. Дані не зберігаються в localStorage.
  Сесійний токен і пароль не потрапляють у JavaScript або технічні журнали.
- Згода з версією та точним текстом, строк зберігання, відкликання, черга запитів
  на видалення, завершення видалення з робочої бази. Відкликану заявку не можна
  поновити звичайною зміною статусу. Бекапи мають окрему обмежену ротацію.
- Перевірені копії SQLite, відновлення лише в новий файл, перевірка цілісності та
  зовнішніх ключів. Тести порівнюють заявки, історію, вакансії й метрики відновленої
  бази з оригіналом.

## Статус перевірених умов MaxHR

Живий імпорт отримав 11 активних проєктів та 17 правил комісій. Усі вакансії
створюються НЕАКТИВНИМИ чернетками з порожньою картою підтвердження. Імпорт не
оголошує суперечливу інформацію погодженою, не публікує її та не перезаписує
відредаговані рекрутером публічні умови. Сирий опис і проблеми з джерелом —
приватні дані для перевірки.

Публікація вимагає підтвердити назву, місто, опис, оплату й графік. У кожного
підтвердженого поля має бути посилання на джерело; в кабінеті зберігається дата
перевірки та подія аудиту. Зміна умови скидає її прапорець підтвердження у формі;
API не дозволяє успадкувати старе підтвердження зміненої умови. Додаткові поля
потрапляють до кандидатів лише після окремої перевірки. Читання аркуша саме по
собі не є погодженням суперечностей агенцією.

Ключові питання перед публікацією: Allegro — базова/нічна ставка; Amazon — години
та сумісність доплат; InPost DC2 — поріг підвищення і години; Empik — верхня
ставка і поточний графік; Anton Röhr — різні ставки; Tedi — відсутня числова
ставка; Carpol — умови оплати пробних днів і підвищення ставки. Повний список
питань залишається у приватному імпорті, а не в кандидатських повідомленнях.

## База і межі масштабування

Для MVP використано спільну СЕРВЕРНУ SQLite у WAL-режимі на постійному диску,
а не сховище браузера. Бот і кабінет працюють з одним сервісним шаром і базою.
Це дає змогу перевірити MVP без нової платної PostgreSQL-служби. Ця версія НЕ є
реалізацією PostgreSQL. Підтримується один сервер/одна репліка із тим самим томом;
горизонтальне масштабування потребує окремої міграції на PostgreSQL. Локальна
перевірка не доводить надійність невідомої production-інфраструктури.

## Запуск для розробки

```sh
python -m pip install -r radar/requirements.txt
python -m radar.preview
```

Preview створює нову тимчасову базу, 11 неперевірених чернеток і синтетичну
сесію перегляду. Тут ніколи не читається production-токен або production-база;
Telegram і реальні анкети вимкнені. Не використовуйте `radar.preview` як
production-команду: це навмисно відкритий тестовий простір без реальних даних.

Кабінет у production: `python -m radar serve` або Dockerfile.radar. Для HTTPS
потрібен платформний TLS reverse proxy та коректний RADAR_TRUSTED_PROXY —
список довірених IP проксі. Ніколи не довіряйте довільним X-Forwarded заголовкам.
Uvicorn access log вимкнено; обробники не логують тіла запитів і телефони.

## Налаштування перед живим запуском

- RADAR_DB_PATH — абсолютний шлях під наявним постійним томом.
- RADAR_SESSION_SECRET — випадковий секрет щонайменше 32 символи.
- RADAR_ADMIN_PASSWORD_HASH — створити локально командою `python -m radar password-hash`;
  пароль вводиться без відображення. У середовище передається лише хеш.
- RADAR_PUBLIC_ORIGIN — точна HTTPS-адреса кабінету, без кінцевого `/`.
- RADAR_TRUSTED_PROXY — лише фактичні довірені проксі платформи.
- RADAR_BOT_ENABLED=0 за замовчуванням. Перед `1` потрібно встановити, де саме
  працює чинний EWU, та погодити контрольоване переключення одного poller.
- TELEGRAM_TOKEN — чинний токен тільки на сервері. Старіша перевірка конкретного
  Railway-сервісу дала 401; це не доводить, що бот не працює в іншому місці.
- RADAR_INTAKE_ENABLED=0 і RADAR_PRIVACY_REVIEWED=0 за замовчуванням.
- Активація потребує обох прапорців `1` та заповнених RADAR_POLICY_VERSION,
  RADAR_CONTROLLER, RADAR_PRIVACY_CONTACT, RADAR_LEGAL_BASIS, RADAR_PRIVACY_TEXT,
  RADAR_RETENTION_DAYS. Текст має описати реальні цілі, правову підставу, строки,
  одержувачів і процедуру прав. Сам прапорець не замінює юридичної перевірки.

Текст згоди, підстава, відповідальні сторони й строки не вигадані та не
затверджені цією реалізацією. Реальний збір контактів залишається вимкненим.
Сповіщення приходять у закритий кабінет (оновлення раз на 30 секунд); персональні
дані не надсилаються у сторонні чати.

## Операційні команди

```sh
python -m radar import-maxhr
python -m radar backup --output /private/path/radar-backup.sqlite3
python -m radar restore --input /private/path/radar-backup.sqlite3 --output /private/path/radar-restored.sqlite3
```

Відновлення відмовляється перезаписувати наявний файл. Перед заміною production-
бази: зупинити записи і polling, зробити копію поточного стану, перевірити нову
копію та погодити можливу втрату пізніших записів. Відновлену базу перед відкриттям
потрібно очистити від прострочених даних і повторно застосувати виконані запити
на видалення; резервна копія не скасовує прав суб’єктів даних.

Службова задача раз на годину очищає прострочені дані й робить перевірений бекап
у каталозі radar_backups поруч із базою. Ротація — не більше 7 днів або коротшого
налаштованого строку. Каталог і копії мають права лише власника. Це копія на
тому самому диску, а не перевірений зовнішній disaster recovery. Перед живим
запуском потрібно визначити окреме захищене місце для зовнішньої копії.

## Верифікація й критерії приймання

23 нові unit/integration тести покривають кандидатський сценарій, згоду,
контакт лише власника, кілька вакансій, джерело, дублікати/паралельні відгуки,
публічну ізоляцію, критерії підбору, неактивні вакансії, права адміністратора,
CSRF, cookie, rate limiting, редагування та ревізії, історію, фільтри, вартість
співбесіди, строки, відкликання, видалення й фактичне відновлення копії.

63 існуючі Python regression тести EWU також пройшли. JavaScript перевірено
`node --check radar/static/app.js`. У браузері перевірено список 11 чернеток,
редактор, збереження внутрішньої примітки та створення мітки з готовим посиланням.
Тестові зміни збережені тільки в тимчасовій preview-базі.

Не підтверджено живий Telegram-сценарій, роботу на фізичному телефоні, production-
TLS/логін, зовнішні бекапи або погодження умов MaxHR/правових текстів. До
визначення фактичного робочого розгортання EWU та цих перевірок цей результат —
реалізований і протестований MVP для перегляду, а не прийнятий production-реліз.
